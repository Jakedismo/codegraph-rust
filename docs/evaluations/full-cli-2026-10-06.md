### Case 3: agentic_context (question)

> How does the LRU cache work in GraphToolExecutor? What gets cached and when?

`GraphToolExecutor` keeps an in-memory, mutex-protected LRU mapping a project/tool/parameter key to the tool’s **final JSON result**. On a cache miss it runs the tool, truncates oversized output if needed, and caches that result; on a hit it returns a clone without rerunning the tool. By default caching is enabled with capacity 100, though `with_limits`/`with_cache` allow configuring it.

In `crates/codegraph-mcp-tools/src/graph_tool_executor.rs`, the executor stores `LruCache<String, JsonValue>` behind `Arc<Mutex<…>>` (lines 51–68). `with_context_window` enables caching at size 100, while `with_limits` constructs the cache at the requested capacity; a zero capacity falls back to 100 (lines 85–155). `cache_key` formats the project ID, tool name, and serialized input parameters as `project:tool:params` (lines 272–275); tests check that equal inputs produce equal keys and different projects are scoped separately (lines 759–802).

During `execute`, after tool-name validation, enabled caching looks up that key: a hit increments `hits` and returns the stored JSON; a miss increments `misses` and proceeds to dispatch the call (the hit log is at line 306; the lookup and dispatch are in `execute`, following `cache_key`). After successful execution, `truncate_if_oversized` runs before insertion, so the cached value is the post-truncation response, including any `_truncated` metadata (lines 198–269). The result is then inserted with `cache.put`; when the cache is full, the LRU policy evicts an entry, and the code updates eviction and current-size statistics. Errors return before insertion, so failed calls are not cached.

The key applies to tool results generally—not just graph database calls—so successful calls across the executor’s implemented tools can be cached, including semantic search results. Since lookup happens before tool execution, a hit also skips semantic-search embedding generation and any reranking. `clear_cache` empties the entries and resets hit, miss, eviction, and current-size counters (lines 176–185); `CacheStats` exposes those counters and the configured maximum size (lines 24–35).

### Case 5: agentic_impact (call_chain)

> Trace the call chain from execute_agentic_workflow to the graph analysis tools

With the `ai-enhanced` feature enabled, `execute_agentic_workflow` prepares a project-scoped `GraphFunctions` and shared `GraphToolExecutor`, then hands the query to Rig. From there, **tool calls are selected dynamically**: the active ReAct path sends each selected tool through its Rig adapter and `CountingExecutor` to a name-based dispatch branch in `GraphToolExecutor`, which calls the corresponding graph function. This is not a fixed run through every graph tool.

**Workflow setup and handoff.** `execute_agentic_workflow` in `crates/codegraph-mcp-server/src/official_server.rs:559–877` loads configuration and storage, constructs project-scoped `GraphFunctions`, checks indexed-node availability, initializes the embedding generator, and creates `GraphToolExecutor`. It then calls `RigExecutor::execute` (`official_server.rs:559–877`). The separate feature-disabled implementation returns an error instead of reaching graph analysis (`official_server.rs:881–893`).

**Rig’s architecture and execution branches.** `RigExecutor::execute` builds a `RigAgentBuilder`, executes the resulting agent, and returns its response, tool-call count, and traces (`crates/codegraph-mcp-rig/src/agent/executor.rs:48–157`). The builder chooses among ReAct/Rig, LATS, and Reflexion (`crates/codegraph-mcp-rig/src/agent/builder.rs:158–167`): ReAct/Rig builds the tool-calling agent; LATS is documented as reasoning without graph-tool calls; Reflexion wraps ReAct (`builder.rs:246–253`). If the primary execution fails, `RigExecutor::execute` also branches to a Reflexion retry (`executor.rs:48–157`). On the ReAct path, provider-specific builders register the graph tools with the agent (`builder.rs:287–428`).

**From a selected tool to graph dispatch.** `GraphToolFactory` exposes the individual graph-tool adapters around a `CountingExecutor` (`crates/codegraph-mcp-rig/src/tools/factory.rs:14–81`). For example, `TraceCallChain::call` packages its arguments and invokes `CountingExecutor::execute` (`crates/codegraph-mcp-rig/src/tools/graph_tools.rs:230–257`). The counting wrapper delegates to the shared `GraphToolExecutor` and records success or error traces (`crates/codegraph-mcp-rig/src/tools/counting_executor.rs:28–89`).

`GraphToolExecutor::execute` validates the tool name, checks the result cache, then branches on that name; it applies result-size limiting and caches successful results afterward (`crates/codegraph-mcp-tools/src/graph_tool_executor.rs:285–388`). The eight alternatives are `get_transitive_dependencies`, `detect_circular_dependencies`, `trace_call_chain`, `calculate_coupling_metrics`, `get_hub_nodes`, `get_reverse_dependencies`, `semantic_code_search`, and `find_complexity_hotspots` (`graph_tool_executor.rs:285–388`). Each handler forwards to its corresponding `GraphFunctions` method, which issues a SurrealDB query; these graph methods are in `crates/codegraph-graph/src/graph_functions.rs:183–691`. For the call-chain example, the handler is `execute_trace_call_chain` (`graph_tool_executor.rs:444–467`), which calls `GraphFunctions::trace_call_chain` (`graph_functions.rs:260–288`).

**Additional branch and return flow.** Semantic search takes a distinct path: its handler generates an embedding, calls graph-enriched search, and applies reranking only if a reranker is configured (`crates/codegraph-mcp-tools/src/graph_tool_executor.rs:548–606, 630–664`). Results and traces return through the counting wrapper to Rig; `execute_agentic_workflow` then parses the answer for the selected analysis type, falls back to trace-based synthesis if parsing fails, and formats the response (`crates/codegraph-mcp-server/src/official_server.rs:724–877`).
